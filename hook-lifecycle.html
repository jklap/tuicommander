Hook Lifecycle

How TUICommander drives an agent's busy / idle / awaiting state from the agent's own hook system — every event, what gets extracted from it, what reaches the wire, and what feature inside TUICommander consumes it on the other end.

The Chain

event → wire → feature

One path, six stages. Every hook — Claude, Gemini, Grok, Codex — travels the same chain; only the map at stage 2 and the payload at stage 3 differ per agent.

Two things happen twice on purpose: the TUIC_SESSION check runs both in the shell guard (stage 2, so an ordinary terminal never even spawns the binary) and inside tuic-hook itself (stage 3, for correctness under direct invocation). And the tty written in stage 4 is resolved natively in stage 3 — no ps, validated against a real PTY by comparing its output to the shell's own tty builtin.

The CLI Surface

7 flags, 4 env vars

By default, stage 3 of the pipeline above is driven by hook_event_name alone — the Claude Code events table below is the derivation table (DERIVATIONS in crates/tuic-hook/src/main.rs). Every flag here overrides its derived counterpart rather than replacing derivation outright; none are required for a plain Claude Code hook. Gemini/Grok/Codex (further down) haven't been verified to send hook_event_name in the same shape, so their maps still pass --state explicitly, exactly as before derivation existed.

--toolfail-from-stdinThe derived toolfail, extracting exit_code itself (legacy alias — kept for a binary/settings version mismatch during rollout).

Environment:

VariablePurpose
TUIC_SESSIONMust be set and non-empty, or every flag above is a no-op.
TUIC_PTY_TTYPrimary tty-resolution mechanism — stamped by TUICommander onto every pty it spawns (spawn_pty_pair_with_retry), so a hook subprocess writes straight back to the pty TUICommander already knows about instead of relying only on an ancestor-process walk.

Unrecognized flags, flags missing their value, and an unrecognized hook_event_name are all silently ignored, never errors — a stale binary meeting a future flag or event must degrade gracefully, not fail the hook. Reading stdin is no longer conditional on which flags are passed: every fire reads it now (bounded, 1 MiB — generous on purpose, since a failed tool call's captured output can be large, and a payload that fails to parse now costs the whole fire's derivation, not just one field), since knowing hook_event_name requires it — measured at roughly half a millisecond of added cost per fire, dominated by process-spawn overhead rather than the read itself. The read runs on a background thread with a 500 ms budget, so a caller whose stdin-closing behavior is unverified (Gemini/Grok/Codex never touched stdin at all before derivation existed) can never hang it; the same thread keeps draining anything written past the 1 MiB cap afterward, so a larger caller write never blocks on a full pipe either.

The headline fix. Used to require jq on PATH to read this payload at all — absent, the whole hook silently no-op'd and red ticks fell back to text-pattern matching. tuic-hook parses the JSON itself, deriving the toolfail extraction from hook_event_name rather than an explicit --toolfail-from-stdin flag. Trade-off: if the payload itself is unparseable, this fire can't be identified as PostToolUseFailure at all, so nothing is emitted — the old explicit flag guaranteed a toolfail=1 fallback even then. Accepted because this JSON is Claude Code's own generated payload, not user input.

Why It's Shaped This Way

4 decisions

Non-obvious choices, previously buried in code comments and defended only by a test name. Each one broke something the first time it was gotten wrong.

No broad, empty-matcher PreToolUse entry

An early version fired a bare busy on every PreToolUse, regardless of tool. It was redundant with UserPromptSubmit's single busy call for the turn-level busy/idle atomic, and it was the root cause of the green-tick scrollbar marker firing once per tool call instead of once per prompt. The narrow AskUserQuestion|ExitPlanMode matcher is deliberate and is guarded by a test (claude_map_has_no_broad_pretooluse_busy_entry) specifically so it doesn't come back.

toolfail always precedes state on the wire

handle_tuic_state reads-and-clears turn_error_flags at the exact moment it processes a state=idle transition. If toolfail arrived after state=idle on the wire, the flag it sets would be read one turn too late — or never, if the next turn ends cleanly. tuic-hook's build_emissions partitions toolfail to the front of the emission list regardless of argv order, so this can't regress by accident.

Success/failure hooks are mutually exclusive branches, not a sequence

PostToolUse fires only on success and carries no error field at all; PostToolUseFailure fires only on failure and carries error and is_interrupt (not exit_code — that field isn't in its real schema). They are two branches of one lifecycle point, never both for the same tool call — same for Stop/StopFailure. Treating them as sequential (checking one, then the other) would double-count or miss a transition.

The shell guard exists twice, and neither copy is redundant

[ -n "$TUIC_SESSION" ] in the installed command avoids spawning tuic-hook at all in an ordinary terminal — worth roughly 4ms per fire on its own. The identical check inside the binary's main() exists for direct invocation (testing, debugging, a future caller that isn't the installed hook command) — dropping either copy re-opens a real gap the other doesn't cover.

Ownership & Install Mechanics

3 strategies

All decided by agent_hook_installer.rs, which is sentinel-keyed and therefore agnostic to what a command actually contains.

Merge

Claude, Gemini, Codex. Prune-then-append into a shared settings.json — every non-sentineled entry (user or wiz hooks) survives untouched.

Own file

Grok. TUIC owns the whole file; install writes it, uninstall deletes it, siblings in the directory are never touched.

Own file + TOML flag

Codex additionally needs [features] hooks = true in config.toml, toggled symmetrically with the hooks file so neither can strand the other.

The Settings badge, from InstallState:

installed — byte-identical to the current map
outdated — sentineled commands present, differ from the current map
not installed — no sentineled commands found

A startup migration (reinstall_outdated_hooks) re-installs any agent that is enabled but Outdated — without it, a user who enabled hooks under an older TUICommander version would keep the old shell-only commands (and the jq dependency) indefinitely, since nothing besides the Settings toggle used to trigger a re-install.
