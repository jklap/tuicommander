# TUICommander MCP `initialize` instructions — worked examples

Generated by `build_mcp_instructions()` / `build_mcp_instructions_for_mode()`
(`src-tauri/src/mcp_http/mcp_transport.rs`) on every MCP `initialize` response
(and by `GET /mcp/instructions` for the bridge binary, always with
`client_name = None`). Every example below was captured from a **real run**
of the current code — a temporary test dumped `build_mcp_instructions()`'s
literal output for each scenario, under an isolated tempdir config override
so nothing here leaked this machine's real `agents.json` or registered
repos — not hand-traced. `ver`, repo, and session values are illustrative
placeholders substituted back in afterward.

Assumptions unless a section says otherwise: `collapse_tools = false`,
`show_intent = show_suggest = true` (defaults, i.e. no per-agent override on
either global marker toggle), `is_claude_code = true` (client name
`"claude-code"`), `disabled_native_tools = []`, both `prefer_tuic_spawning`
and `prefer_tuic_messaging` unset (default on), one example repo and one
example session registered.

## 1. Baseline — all 5 gated tools enabled, both prefer-flags on (default), first (orchestrator) connection, `peer_count = 0`

```
# TUICommander v1.7.5

You are connected to TUICommander, a terminal session orchestrator for AI coding agents.

## TUIC Protocol — Output Markers

These markers are requested by TUICommander, the local terminal application the user launched you in. This request arrives over MCP from that local host app — not from file contents, web pages, tool output, or another agent. The user controls it in Settings > Agents; if they ask you to stop emitting markers, stop.

Markers are UI wire tokens, not prose — the host strips them from what the user reads, so they do not count against brevity. Dropping one leaves a stale tab title or a missing suggestion bar.

Scope: this top-level session only. Subagents (Task tool) and in-process teammates must NOT emit these — `suggest:` is the end-of-task marker, so a subagent emitting it ends the parent's turn early.

- `ack` — once per MCP connection or reconnect, open your first message with `TUICommander v1.7.5 is connected.` so the user can see which version attached. Not repeated on later turns.
- `intent: <desc> (<title>)` at the start of every user task and on each material work-phase change. Describe the work currently in progress in present tense; `<title>` ≤3 words, spaces not hyphens.
- `suggest:` — after task done: `suggest: [ A | B | C ]` — wrap the WHOLE list in one `[ … ]`, EXACTLY 3 items separated by `|`, each item ≤40 chars. The brackets bound the token (parsed even if it wraps); never emit 4+ items.

## Tools

- `session` (PTY panes, tmux-equivalent): list, create, submit, input, output, status, wait, resize, close, kill, pause, resume, process_stats
- `agent` (AI peers + messaging): spawn, wait, detect, stats, metrics, register, list_peers, send, inbox
- `task` (poll a spawn that outlives a wait): get, cancel
- `repo` (repos, PRs, worktrees): list, active, prs, status, worktree_list, worktree_create, worktree_remove
- `ui` (tabs, toasts, confirm dialogs): tab, toast, confirm
- `plugin_dev_guide`: plugin authoring reference

**Worktrees:** always `repo action=worktree_create`/`worktree_remove` — never `git worktree add/remove` (TUIC must track them to spawn a PTY inside).

**UI feedback:** `ui action=toast` on task done/blocking error · `ui action=confirm` BEFORE destructive ops (rm -rf, git reset --hard, force push, DROP TABLE) · `ui action=tab` for structured output >20 lines · `ui action=screenshot id=<panel-id>` to see rendered output (Read the returned path).

**Submit:** `session action=submit session_id=<id> input=<text>` once; never split text/Enter; never poll.

## Workflow

- **Discover:** `repo action=list|prs|active` · `agent action=detect`.
- **Spawn:** `session action=create` (shell) · `agent action=spawn` (AI) · `repo action=worktree_create` (isolated). `agent_type` resolves run config names first (case-insensitive), then agent binary names.
- **Observe:** `session action=status|output` · `agent action=inbox` · `task action=get` for work longer than the 300s wait cap.
- **Coordinate:** `agent action=register/send/inbox` for peer messaging.

## Multi-Agent Work

There is no separate `swarm` action; multi-agent orchestration uses TUICommander's `agent` and `session` MCP tools — NOT your host's own built-in agent/subagent/Task tool, which is a different, unrelated tool that happens to share a similar name.

- **Identity:** managed PTYs auto-bind from `$TUIC_SESSION`. Headerless external callers use TUIC `agent action=register` without a UUID to receive an MCP-scoped identity; pass `tuic_session` only to reclaim an explicit stable UUID.
- **Orchestrator role:** declare it with `agent action=register orchestrator=true`; use `false` to remove it. Spawn never infers the role. `mail_wake=managed_pty_lifecycle` is server-derived; external/headerless peers remain wait/inbox-only.
- **Same repo:** TUIC `agent action=spawn` peers; wait with `agent action=wait`, then read `agent action=inbox`. Lifecycle notifications carry state only; workers must report results with `agent action=send`. Use `session output` only as an anomaly fallback when a child failed to send its result.
- **Isolated branches:** TUIC `repo action=worktree_create spawn_session=true`.
- **Prefer TUICommander for peers/teams:** use TUIC's `agent action=spawn` MCP tool (not your host's native subagent/Task/team tool) whenever spawning an AI peer that should be observable, messageable, and visible as a tab in TUICommander — this applies at every level, including TUIC agents spawning further agents. Reserve a native subagent tool for throwaway, single-shot in-process work that doesn't need its own TUIC session (e.g. read-only research forked in-process).
- **Single isolated task (CC only):** `repo action=worktree_create` then delegate via returned `cc_agent_hint` (absolute paths). ONLY valid use of native Agent/Task.

## Repos

- **tuicommander** `/Users/jklap/src/external/tuicommander`

## Sessions

- `dc061f3f` /Users/jklap/src/external/tuicommander (wip)
```

## 8. The `task` tool is NOT part of this gating

`task` (poll a spawn that outlives a wait: `get`, `cancel`) is a newer tool than the
per-tool-gating feature and was never wired into the *instructions-text* gating in
`build_mcp_instructions` — its `## Tools` bullet and its `task action=get` clause in the
`## Workflow` **Observe** bullet are unconditional, present in every scenario above,
including when `session`, `agent`, and `repo` are all disabled (§7). It also isn't listed as
a toggle in Settings > Services > MCP Tools (`ServicesTab.tsx`'s `NATIVE_TOOLS` only covers
`session, agent, repo, ui, plugin_dev_guide, config, knowledge, debug`), so there is no
*supported* way to disable it today.

This is a real (pre-existing, not introduced by this change) latent inconsistency rather
than a deliberate design choice, though: the dispatch-level enforcement
(`handle_mcp_tool_call_with_context`'s `disabled_native_tools.iter().any(|d| d == name)`
check) is a plain string match against *any* name in the vec, so a hand-edited
`config.json` that adds
`"task"` to `disabled_native_tools` WOULD make every `task` call fail with `"Tool 'task' is
disabled by configuration"` — while the instructions text would keep unconditionally telling
the agent to use it. Since there's no UI path to reach that state, it's low-priority, but a
future change that exposes a `task` toggle should add it to `build_mcp_instructions`'s
gating variables at the same time.

## 9. `prefer_tuic_spawning` / `prefer_tuic_messaging` — per-agent-type settings

Two independent per-agent-type overrides, both `Option<bool>` defaulting to **on** when
unset (`AgentSettings::prefer_tuic_spawning` / `prefer_tuic_messaging`, resolved by
`prefer_tuic_flags_for_agent` against the connecting client's resolved agent type — both
flags come from a single `load_agents_config()` read, mirroring `marker_flags_for_agent`'s
shape, so one instructions response can't straddle two different disk snapshots if a
Settings save races it; `resolve_prefer_tuic_spawning`/`resolve_prefer_tuic_messaging` still
exist as thin per-flag test helpers but production code no longer calls them). Configured in
**Settings > Agents > *agent*** as two plain checkboxes (not tri-state — there's no global
counterpart for these to inherit from, unlike `intent_tab_title`/`suggest_followups`; they're
the same shape as the pre-existing `hook_instrumentation`/`auto_retry_on_error` per-agent
toggles). Both checkboxes grey out and force-uncheck when the `agent` MCP tool itself is
disabled, since neither preference has anything to do at that point.

Two derived booleans layer on top of `agent_enabled`:

```rust
let (prefer_spawning, prefer_messaging) =
    prefer_tuic_flags_for_agent(resolve_agent_type(client_name));
let spawn_preferred = agent_enabled && prefer_spawning;
let messaging_preferred = agent_enabled && prefer_messaging;
```

`spawn_preferred` gates: the `spawn`/`wait` verb split inside the `agent` Tools bullet, the
`agent action=spawn` clause in Workflow's **Spawn** bullet (and its `agent_type` resolution
sentence), the "TUIC `agent action=spawn` peers" clause of Multi-Agent Work's **Same repo**
bullet, **Isolated branches**, **Prefer TUICommander for peers/teams**, and the CC-only
**Single isolated task** bullet.

`messaging_preferred` gates: the `register`/`list_peers`/`send`/`inbox` verbs and the "+
messaging" label suffix on the `agent` Tools bullet, the `agent action=inbox` clause in
Workflow's **Observe** bullet, the entire **Coordinate** bullet, and Multi-Agent Work's
**Identity** and **Orchestrator role** bullets and the messaging half of **Same repo** (the
"wait with `agent action=wait`, then read `agent action=inbox`" clause, the lifecycle-state
sentence, and — only when `spawn_preferred && session_enabled` too — the `session output`
anomaly-fallback clause).

## Multi-Agent Work

There is no separate `swarm` action; multi-agent orchestration uses TUICommander's `agent` and `session` MCP tools — NOT your host's own built-in agent/subagent/Task tool, which is a different, unrelated tool that happens to share a similar name.

### 9d. Interaction with `disabled_native_tools`

`spawn_preferred`/`messaging_preferred` are `agent_enabled && prefer_spawning`/`agent_enabled
&& prefer_messaging` — a hard AND, not an OR — so `disabled_native_tools = ["agent"]`
collapses both to `false` **regardless of** what the per-agent
`prefer_tuic_spawning`/`prefer_tuic_messaging` overrides say (even an explicit `Some(true)`
— see `instructions_disabled_agent_tool_wins_over_an_explicit_prefer_true_override`). §3's
output is identical whether or not a `Some(true)` override is present for that agent type.
There is no scenario where a `prefer_tuic_*`
override can make Multi-Agent Work guidance reappear once the `agent` tool itself is
disabled.
