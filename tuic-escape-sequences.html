OSC Sequences

14 recognized

Dispatched from a single match statement in Performer::osc_dispatch (ansi.rs:1361–1577). Two exceptions — progress and notifications — bypass the parser entirely and are pulled from raw PTY bytes with regex.

Title & directory

OSC 0 / 2Window & icon title

Grammar: both codes hit the exact same match arm (ansi.rs:1363–1376) — TUIC makes no distinction between "icon title" (0) and "window title" (2). Params from index 1 onward are UTF-8-decoded, joined with ;, then trimmed, and handed to set_title(Some(title)). A bare \x1b]0;\x07 with nothing after the semicolon falls through to unhandled().

Downstream: the real handler stores the title and emits Event::Title (or Event::ResetTitle when cleared) — picked up as TermEvent::Title(t) in terminal_grid.rs:48–49 and read again in pty.rs:4457 to relabel the pane/tab in the UI.

\x1b]0;My Title\x07 # identical effect to OSC 2 \x1b]2;My Title\x07
OSC 7Working directory

Reports the shell's current directory as a file:// URL, forwarded to osc7() so TUIC can track cwd per pane.

\x1b]7;file://myhost/home/user/project\x07

Color & appearance

OSC 4Palette get/set

Grammar: needs an odd, >1 total param count — index/color pairs (ansi.rs:1393–1417); anything else is dropped via unhandled(). The index is read by a hand-rolled decimal parser clamped to u8 (0–255). Colors accept two formats via xparse_color() (ansi.rs:180–227):

FormatExampleNotes
Legacy hex#rgb / #rrggbb / #rrrgggbbbtruncated/filled to 8 bits per channel
XParseColorrgb:r/g/beach channel scaled from however many hex digits are given — rgb:f/f/f is full white

A color of ? is a real query, not a no-op — TUIC writes an actual report back down the PTY via dynamic_color_sequence(), doubling each byte to fake 16-bit-per-channel X11 reporting: \x1b]4;{index};rgb:{rr}{rr}/{gg}{gg}/{bb}{bb}<terminator>.

Set: \x1b]4;1;#ff0000\x07 Query: \x1b]4;1;?\x07 Response: \x1b]4;1;rgb:ffff/0000/0000\x07
OSC 10 / 11 / 12Foreground / background / cursor color

Same get/set shape as OSC 4, but for the three fixed slots rather than a palette index — the offset from 10 selects which one.

Query fg: \x1b]10;?\x07 Set bg: \x1b]11;#000000\x07
OSC 104Reset palette

With no params, resets all 256 palette entries. With params, resets only the listed indices.

All: \x1b]104\x07 Indices: \x1b]104;5;6\x07
OSC 110 / 111 / 112Reset fg / bg / cursor color

No parameters — each just reverts one of the three fixed color slots to default.

\x1b]110\x07 /* fg */ \x1b]111\x07 /* bg */ \x1b]112\x07 /* cursor */
OSC 22Mouse cursor icon

Grammar: exactly 2 params required (ansi.rs:1483–1489). The shape string is matched against CursorIcon::from_str — the full standard CSS3 cursor keyword set, and nothing else:

default · context-menu · help · pointer · progress · wait · cell · crosshair · text · vertical-text · alias · copy · move · no-drop · not-allowed · grab · grabbing · e-resize · n-resize · ne-resize · nw-resize · s-resize · se-resize · sw-resize · w-resize · ew-resize · ns-resize · nesw-resize · nwse-resize · col-resize · row-resize · all-scroll · zoom-in · zoom-out · dnd-ask · all-resize

An unrecognized string logs debug!("[osc 22] unrecognized cursor icon shape…") and is dropped — there's no fallback icon, the pointer just stays whatever it already was.

\x1b]22;grab\x07
OSC 50Text cursor shape

App-level override of the caret style, independent of DECSCUSR. 0 = block, 1 = beam, 2 = underline.

\x1b]50;CursorShape=1\x07

Hyperlinks & clipboard

OSC 8Hyperlinks

Grammar: requires more than 2 params (ansi.rs:1420–1446). The URI is rebuilt from params[2] plus any further params rejoined on ; — needed because a literal ; inside the URI itself gets split apart by the OSC parser and has to be stitched back together; there's no length cap. An empty URI closes the link (set_hyperlink(None)).

The field before the URI is split on : into key=value pairs — only id= is recognized; e.g. id=42:foo=bar still only extracts id, the rest is ignored.

No nesting: the link is stored on the cursor's cell template, the same way an SGR color is — there's no stack. Opening a second OSC 8 before closing the first just overwrites the template; every cell after that gets whichever link was set most recently.

\x1b]8;id=42;https://example.com\x1b\link text\x1b]8;;\x1b\
OSC 52Clipboard

The base64 payload passes straight through to clipboard_store() undecoded; a ? payload requests the current contents back via clipboard_load().

Set: \x1b]52;c;SGVsbG8=\x07 Query: \x1b]52;c;?\x07

Shell integration & agent protocol

OSC 133Prompt / command marks

Grammar: \x1b]133;COMMAND[;PARAMS]<BEL|ST>. In ansi.rs:1550–1563 the command is read as params[1][0] (a single letter); the payload comes from whatever follows it — either the rest of that same param (if a literal ; immediately follows the letter) or a separate third param, e.g. D;42 parses as ["133","D","42"].

Recognized command letters — alacritty_terminal/term/mod.rs:2625–2642
LetterCell type appliedMeaning
APromptPrompt is being drawn
BInputPrompt ended, user input begins
COutputCommand execution / output begins
DNoneCommand finished — params carry the exit code

Any other letter hits the fallback arm and returns before an event is even built — no TermEvent::Osc133 is emitted for it. And although the parser accepts B, TUIC's own bash/zsh/fish hooks never send it — only A, C, and D — it's recognized purely for compatibility with other tools (FinalTerm/iTerm2-style) that do emit it.

printf '\e]133;A\a' # prompt start (real preexec hook output) printf '\e]133;C\a' # about to run printf '\e]133;D;%d\a' "$ec" # done, exit code 42 for example \x1b]133;D;0\x1b\ # ST terminator works identically to BEL

Zone extraction: extract_semantic_zones() (terminal_grid.rs:1195–1239) walks the grid and coalesces contiguous same-typed cells into (prompt|input|output, start_line, end_line, text) tuples. That's how TUIC hands an agent "just the command" or "just the output" without falling back to raw screen-scraping.

A→ prompt drawn typed text + C→ exec starts output + D;0→ zone closed, exit 0 A again→ next prompt

That exact interleaving — including an OSC 7770 suggest= riding along in the same chunk — is covered by the integration test osc7770_and_osc133_full_flow (terminal_grid.rs:3651–3693).

OSC 7770TUIC agent protocol proprietary

Grammar: \x1b]7770;VERB=PAYLOAD<BEL|ST>, dispatched inside vte at ansi.rs:1565–1574. The body is split on the first = only. No = at all means the whole sequence is dropped before the handler is even called — Handler::osc7770() never runs. The real implementation (alacritty_terminal/term/mod.rs:2650–2658) stamps the current cursor line and emits Event::Tuic{verb, payload, line} — the payload is never written to the visible grid (verified by osc7770_not_written_to_grid, terminal_grid.rs:3574–3582).

Verbs actually wired up by TUIC's shell hooks
VerbPayload shapeEmitted by
statefree-text token, e.g. idle, busytuic_state()
suggestpipe-delimited action listtuic_suggest()
intentfree-text description of current activitytuic_intent()

The parser itself is verb-agnostic — anything before the first = is accepted and forwarded as-is. Only these three are actually sent by the shell integration scripts or consumed downstream; there's no error, done, or progress verb.

\x1b]7770;state=idle\x07 \x1b]7770;suggest=Fix the bug|Run tests|Deploy\x07 \x1b]7770;intent=Refactoring auth module (Auth Refactor)\x07 \x1b]7770;state=busy\x1b\ # ST terminator, same result as BEL \x1b]7770;garbage\x07 # no '=' → silently dropped \x1b]7770;state=\x07 # empty payload is valid: verb="state", payload=""

Separate from the escape channel: if a line of plain text at the cursor literally starts with suggest: or intent:, it's excluded from certain scans while still being typed (terminal_grid.rs:3605–3648) — a heuristic safety net for shells/agents that print these as visible text instead of the OSC sequence.

Progress & notifications bypasses vte

These two never reach osc_dispatch — output_parser.rs regexes the raw PTY stream for them directly.

OSC 9;4Progress reporting

Grammar: parse_osc94() matches \x1b\]9;4;(\d);(\d{1,3}) (output_parser.rs:815–829). The percent value is clamped to .min(100).

The state digit carries no enumerated meaning in TUIC — unlike ConEmu/Windows Terminal's real OSC 9;4 spec, where 0/1/2/3/4 mean normal/running/error/indeterminate/paused, TUIC's consumer (state.rs:3242–3253) only checks one thing: state 0 always clears the progress value, any other state sets it. A state of 2 ("error" in the real spec) still just renders as a plain progress bar — there's no error styling.

Show 75%: \x1b]9;4;1;75\x07 "Error" 50%: \x1b]9;4;2;50\x07 # still renders as plain 50% — no error state Clear: \x1b]9;4;0;0\x07
OSC 777Desktop notification → question detection

Grammar: \x1b]777;notify;TITLE;BODY<BEL|ST>, matched by parse_osc777_notifies() (output_parser.rs:852–883) against the regex \x1b\]777;notify;([^;\x07\x1b]*)(?:;([^\x07\x1b]*))?(?:\x07|\x1b\\). The text actually tested is the body if it's non-empty, otherwise the title falls back into its place.

Complete keyword list (case-insensitive substring match) — output_parser.rs:873–876
PhraseResult
"needs your permission"Question{confident: true}
"approval required"Question{confident: true}
"is waiting for your input"Question{confident: false}

Nothing else qualifies — including the deliberately excluded "Claude Code needs your attention" (output_parser.rs:834–839), which was dropped on purpose because it also fires on ordinary turn completion, not just real questions.

\x1b]777;notify;Approval required;Run rm -rf build/?\x07 \x1b]777;notify;Claude needs your permission;\x07 \x1b]777;notify;Claude is waiting for your input;\x07 \x1b]777;notify;Claude Code needs your attention;\x07 # ambiguous — no event at all

End-to-end: the resulting Question is one input among several — alongside a silence-timer and screen-scrape heuristic in pty.rs — feeding a state machine that flips session.awaiting_input (state.rs:258, 402, 3080–3234). This is not a blocking modal: it surfaces as a session status flag/badge and can trigger a push notification via relay_client.rs (reason: "awaiting_input").

regex match→ Question{confident}→ awaiting_input = true→ status badge + push notify

A confident question only clears once the user actually types something. An unconfident one auto-retracts on its own (emit_question_cleared_if_stale, pty.rs:3669) once the screen goes quiet with no visible prompt on it.

Explicitly not handled

  • OSC 9 (plain, without ;4) — falls through to unhandled(), logged and dropped.
  • OSC 1337 — iTerm2's inline image / file-transfer protocol has no handler anywhere in the codebase.
  • OSC 6, 21 and any other unlisted number — same silent drop via unhandled().

Cursor & Mouse

CSI-level behavior, plus the private DEC modes (CSI ? Ps h/l) that switch mouse reporting and cursor-key encoding on and off.

DECSCUSRCursor style

CSI Ps SP q — sets block, underline, or beam. Odd Ps blinks, even is steady; 0 resets to the terminal default. (ansi.rs:1765–1780)

\x1b[5 q /* blinking beam */
DECCKMApplication cursor keys — mode 1

When set, arrow keys and Home/End are re-encoded as SS3 sequences (ESC O A…) instead of the normal CSI A form, so full-screen apps like vim and less get the encoding they expect. (terminal_grid.rs:1613)

Enable: \x1b[?1h Disable: \x1b[?1l
Mouse-reporting private modes — ansi.rs:911–936
ModeNameBehavior
1000ReportMouseClicksX10/normal click reporting
1002ReportCellMouseMotionMotion reported while a button is held
1003ReportAllMouseMotionEvery motion event, button or not
1004ReportFocusInOutPane focus gained/lost events
1005Utf8MouseUTF-8 coordinate encoding
1006SgrMouseSGR coordinate encoding — what TUIC actually emits on the wire
1007AlternateScrollWheel events become arrow keys in the alt screen

No separate urxvt-style (1015) path — the SGR encoding (1006) covers it. A recent fix stopped SGR mouse reports from leaking stray bytes into the input buffer (test: sgr_mouse_report_does_not_leak_into_content).

Under any-motion tracking (1003), TUIC's own sgrMotionButton() (canvasTerminalUtils.ts) reports which button is actually held during the drag (left > middle > right priority, "no button" only on a bare hover) — an earlier version hardcoded SGR button 3 ("no button") on every motion event regardless of what was held, which silently broke click-and-drag text selection inside apps that rely on motion reports for drag tracking (e.g. Claude Code's own Ink-based UI). Test: sgrMotionButton.test.ts.

Reverse (7)Reverse video & background-color-erase

SGR 7 sets Flags::INVERSE on the cursor's cell template (Attr::Reverse / Attr::CancelReverse for 27, alacritty_terminal/term/mod.rs:2236–2237); the renderer swaps fg/bg for any cell carrying it — there's no separate "standout" attribute, just this one flag.

Background-color-erase: when the pen has Reverse active, explicit erase commands (EL / ED / ECH / DCH / ICH) carry the reverse flag — and the fg it swaps in — into the blank cells they write, via Cell::erase_blank() (term/cell.rs). Upstream alacritty's erase paths only ever propagated the background color, so tput smso; tput el used to paint a plain gap instead of a highlighted bar to the edge, unlike xterm/VTE. Row recycling from a scroll or hard reset (GridCell::reset) deliberately does not carry the reverse pen — an earlier version of this fix routed it through erase_blank() too, which bled a highlighted line's reverse pen onto every later-recycled blank row; reverted to constructing the blank directly. Underline and strikeout also deliberately do not ride along the erase paths — terminals disagree on whether BCE extends those, and picking wrong smears an attribute across erased space instead of just leaving it unhighlighted. Covered by erase_in_line_with_reverse_pen_fills_bar_to_edge, scroll_up_with_reverse_pen_does_not_fill_new_row_reverse, and erase_chars_and_delete_chars_carry_reverse_pen (terminal_grid.rs).

This is cell-level only — there is no screen-wide reverse video. See DECSCNM in Screen & Terminal Modes.

printf 'ab\e[7m\e[K' # "ab" plain, then EL under a reverse pen — cols 2.. fill as a highlighted bar to the edge

Device Control Strings

hook / put / unhook (ansi.rs:1324–1337) exist only as empty stubs.

Parsed, not acted on

  • DCS frames are recognized structurally by vte so the parser doesn't desync, but the payload is discarded.
  • No Sixel graphics, no DECRQSS status reports, no tmux passthrough.
  • No APC (Application Program Command) handling either.

Deliberate Deviations

Fixes where TUIC diverges from naive spec-following to keep real-world apps usable, per recent commit history.

Reverse-video erase

Vendored alacritty's explicit erase paths only ever propagated the pen's background color into blank cells — the xterm/VTE background-color-erase convention, but just the background half of it. A pen with SGR 7 active lost the reverse flag (and swapped foreground) on EL/ED/ECH/DCH/ICH. Patched via Cell::erase_blank() so those blanks carry reverse video too, matching real terminals. Rows scrolled or reset in while reverse are deliberately not patched the same way — an earlier attempt at this routed row recycling through erase_blank() too, which leaked a highlighted line's reverse pen onto every later-recycled blank row; reverted to keep row recycling's blank construction plain — see Reverse (7).

Input safety

SGR mouse reports (mode 1006) were leaking raw bytes into the pane's typed-input buffer under some timing; the parser now consumes them fully before they can reach line content.

Cursor width

The cursor cell now widens to cover full double-width glyphs (CJK, emoji) instead of highlighting only the leading half.

Cursor keys

DECCKM (mode 1) is honored for arrows, Home, and End, and apps are allowed to set the cursor shape themselves rather than TUIC always overriding it.

Scroll input

Forwarded wheel events are quantized to whole notches and acceleration is capped, so a fast trackpad swipe doesn't flood an app with scroll events.
