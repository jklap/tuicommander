Agent Signal Architecture

Every way TUICommander learns whether an agent is busy, idle, or blocked waiting on you — and how three completely different origins (a hook protocol we invented, a notification format we don't control, and reading the rendered screen) all converge into one SessionState and one pair of scrollbar ticks. Read this first; hook-lifecycle.html and tuic-escape-sequences.html go deep on one piece each.

Companion to hook-lifecycle.html (the hook→OSC 7770 pipeline in detail) and tuic-escape-sequences.html (every wire sequence TUIC parses, either direction). Three Origins, Same Destination

hooks · notify · screen

Nothing downstream cares which of these three fired — a ParsedEvent looks the same regardless of origin. But the three could not be more different in who controls them, which is exactly what makes the boundary between them easy to misdescribe (this doc's own first draft got it wrong once — see OSC 777 vs 7770).

Hook protocol OSC 7770

TUIC-invented · TUIC-controlled

We install a hook command into the agent's own settings file. When Claude Code (or Gemini/ Grok/Codex) fires a hook event, that command runs tuic-hook, which writes ESC]7770;verb=payload straight to its own controlling tty. Every verb, every payload shape, and every event→verb mapping is ours to define — see hook-lifecycle.html in full.

Off entirely if the user hasn't enabled "Native Hook Instrumentation," or if the hook binary/settings entry has drifted — TUIC can tell the difference (hook_state_seen, InstallState) and falls back accordingly.

Native notification OSC 777

Agent-owned (believed) · not TUIC-controlled

ESC]777;notify;TITLE;BODY — a pre-existing terminal convention (rxvt-unicode's desktop-notification extension) that output_parser.rs::parse_osc777_notifies() was written to catch as a fallback signal for whatever hooks can't reach (plan/skill pickers).

Empirically retested 2026-08-29 and found to not appear even in a scenario built specifically to trigger it. See OSC 777 vs 7770 — this box may be documenting a mechanism that no longer fires for hook-instrumented Claude.

Screen-scrape rendered rows

Universal fallback · fragile by nature

Read the terminal grid TUIC already renders and look for agent-specific patterns: an Ink footer, a cliclack ◆ prompt, a spinner row, a composer glyph, a title string. The only mechanism available to an agent with no hook support at all (Aider, Amp, Cursor, Droid, pi) or as the fallback half of a hook-instrumented one (plan/skill pickers, which fire no hook state at all — see hook-lifecycle.html).

Explicitly suppressed for hook-instrumented sessions where the hook already covers the same ground (suppress_heuristic_question), so the two don't double-fire.

The Whole Pipeline

origin → event → state → consumer

Four consumers read off the same SessionState, and two more read a parallel CommandBlock stream that's fed by a structurally different subset of the same three origins (see Command Blocks).

The dashed line is deliberate: only the hook's state=busy/idle transitions feed CommandBlock directly (via handle_tuic_state). The OSC 777 and screen-scrape boxes above only ever reach SessionState, never blocks — screen-scraped blocks come from a completely separate detector (synthesize_cc_block_events) that isn't shown twice on this diagram only to keep it legible. OSC 777 vs OSC 7770

one digit, two unrelated systems

The names collide on purpose — both happen to use the word "notify" — and that's the entire source of the confusion this section exists to kill.

The empirical test (2026-08-29)

Spawned a fresh hook-instrumented Claude session, gave it a one-word trivial task, let it go idle, then waited 90 seconds — past the documented ~60s idle-timer threshold that's supposed to make Claude emit "Claude is waiting for your input" as a notification. Captured the raw PTY bytes (/diagnostics/capture) and classified every OSC 777x sequence by exact digit count:

\x1b]7770;notify=Claude%20is%20waiting%20for%20your%20input \x1b]7770;state=awaiting

Zero occurrences of \x1b]777;notify;… (three sevens). What actually happened: Claude Code's Notification hook event fired (a real Claude Code hook, not an escape sequence), and our own tuic-hook converted it into the OSC 7770 notify= verb plus a separate state=awaiting verb — exactly as hook-lifecycle.html's Notification card already describes. No native OSC 777 was involved at any point.

This does not prove OSC 777 never fires — only that it didn't fire here, for a hook-instrumented session, for exactly the scenario its own doc comments describe. Whether it's a real fallback for non-hook-instrumented Claude, a signal from an older CLI version, or fully dead code is unconfirmed — testing it would mean disabling hook instrumentation globally, which affects every other live Claude tab, so it wasn't done casually mid-session. Treat parse_osc777_notifies() as unverified-in-current-practice, not as confirmed-dead — the honest state is "we don't know," not "it's gone."

The confidence gap this reveals fixed 2026-09-02

tuic_state_awaiting_event() used to map every hook-sourced state=awaiting to ParsedEvent::Question{confident: true}, unconditionally — it had no way to know whether the underlying Claude Code hook event was PreToolUse(AskUserQuestion) (always a genuine block) or Notification (which fires for a genuine block and for Claude's own ~60s idle-timer heartbeat, using the same ambiguous wording, and TUIC cannot tell them apart from the hook payload alone).

The never-actually-firing OSC 777 parser, ironically, already solved this exact problem for the path it covers: it deliberately marks "is waiting for your input" as confident: false specifically because of this ambiguity, which lets the silence-timer retraction backstop (emit_question_cleared_if_stale) clear a false alarm once the screen goes quiet with nothing really pending. The hook path used to have no equivalent — a confident question is designed to stay sticky until real user input, which is correct for a genuine AskUserQuestion block and was wrong for an idle-timer false alarm wearing the same state=awaiting costume. This was the actual, precise mechanism behind a class of "badge stuck on awaiting, but the agent is genuinely idle and has been for 20+ minutes" reports — not a broken retraction path, a hook signal that was more confident than its own source event justified.

Fix: rather than only sniffing message wording the way the OSC 777 parser has to, tuic-hook now also scrapes Claude Code's own notification_type field (a closed set of 12 values as of this writing) as a new notifytype verb, paired with notify immediately before every Notification-sourced state=awaiting. pty.rs's notification_awaiting_outcome classifies deterministically off it — permission/ elicitation/quota-stale types stay confident, purely informational types (auth success, a background session finishing, …) never badge awaiting at all, and idle_prompt is dropped outright when the shell is already idle (a real Stop already fired) but still surfaces non-confidently mid-turn. The wording classifier survives as the fallback for a notification_type this binary predates or an older Claude Code build that never sends the field. PreToolUse/Elicitation still never scrape either field, so they're unaffected — always confident. See the matching Incident Log entry for the full mechanism and the tests covering it.

Command Blocks & Scrollbar Ticks

2 producers, 1 dead verb, 2 tick colors

The scrollbar's colored ticks are driven by the exact same three-origin split as awaiting_input — but through a structurally different event (AgentBlock, not Question) with its own one-way switch between producers.

ParsedEvent::AgentBlock

{ action: "start"|"end", line, exit_code: Option<i32>, prompt_text: Option<String> }. Two producers, mutually exclusive per session for its whole lifetime:

Hook-drivenScreen-scraped fallback
Functionhandle_tuic_statesynthesize_cc_block_events
TriggerA real state=busy/state=idle CAS edge (not a re-affirmation)A Claude Code ⏺ ToolName(…) tool-call header appearing on screen
GranularityOne block per whole busy→idle turnOne block per tool call — finer-grained
exit_codeFrom turn_error_flags, read-and-cleared at the idle edgeAlways None — no text source available
prompt_textThe submitted prompt, on block startAlways None

The switch: state.has_tuic_state_integration flips permanently the FIRST time any OSC 7770 state= event is seen for a session, then the hook path is authoritative for the rest of that session's life — with a one-shot cleanup that closes any block the screen-scrape heuristic had left open at the moment of the switch, so a mid-turn hook detection can't orphan an open block forever.

Dead on the emit side — the OSC 7770 block=start / block=end;<exit_code> verb is fully parsed and unit-tested in pty.rs, but nothing in tuic-hook or agent_hook.rs ever emits it — grepped both, zero hits beyond the unrelated English word "block". The only real hook-driven block source is handle_tuic_state's synthesis off the ordinary state=busy/idle verbs, described above. This is the same shape of trap as the OSC 777 case in this doc — a reachable-looking parser that isn't actually reachable in production. Don't assume a wire verb is live just because it parses cleanly and has a passing test; check the emit side too.
OSC 133 semantic zones — a different system, do not conflate

Shell-integration prompt marks (A/B/C/D, full grammar in tuic-escape-sequences.html) tag terminal grid cells directly as alacritty's handler sees them arrive. extract_semantic_zones() then walks the current screen on demand and coalesces contiguous same-tagged cells into (prompt|input|output, start_line, end_line, text) tuples — a query over rendered state, not an event stream. This is shell-command-level (one real shell command = one triple), used by anything wanting "just the command" or "just the output" text.

AgentBlock is agent-turn-level (or per-tool-call, for the scrape fallback), pushed continuously as a discrete event stream. The two mechanisms are structurally unrelated in the backend — but they do converge, deliberately, one layer up.

Nobody writes these marks by default — TUIC injects a shell hook that does, and the injection mechanism is a completely different trick per shell (src-tauri/src/shell_integration.rs, ~4ms per prompt/command):

ShellInjection mechanismHook equivalentStatus
zsh The ZDOTDIR trick: TUIC points ZDOTDIR at its own wrapper directory, whose .zshenv sources the integration script first, then restores the real ZDOTDIR and re-sources the user's actual .zshenv. Passthrough wrappers for .zprofile/.zshrc/.zlogin/ .zlogout just delegate to the user's real files (plus a compinit -C safety net, since the trick can skip system completion setup). zsh's own precmd_functions/preexec_functions hook arrays — the integration script appends to them, it doesn't replace anything the user already has there. Fully automatic — works transparently, no user action, doesn't touch the user's own dotfiles on disk.
bash Script is written to disk and an env var (TUIC_SHELL_INTEGRATION) is set pointing at it — nothing currently sources it for an interactive shell. Would-be mechanism, present in the script itself: PROMPT_COMMAND (bash's closest analogue to precmd) prepended non-destructively, plus a DEBUG trap (fires before each simple command — bash's closest analogue to preexec), gated by a __tuic_preexec_ready flag so the trap doesn't double-fire against PROMPT_COMMAND's own internal command execution. Not auto-wired. Confirmed by grep: TUIC_SHELL_INTEGRATION is set in shell_integration.rs and read nowhere else in the codebase. An interactive bash session today gets no automatic OSC 133 marks — the code's own comment says "for interactive login shells we rely on the user sourcing it or a future --init-file approach." Cleanest of the three: no polyfill needed, fish already has the exact hooks zsh has. Not auto-wired, same gap as bash.

Net effect: real shell-command blue/red scrollbar ticks and CommandOverview entries — the OSC-133 half of the convergence below — currently only happen for zsh sessions in practice. Bash and fish users get the exact same AgentBlock-driven ticks for AI agent turns (that path doesn't depend on shell integration at all), just not for their own plain shell commands.

Frontend convergence

An agent-block wire event is handled in Terminal.tsx by directly reusing the OSC-133 handler: action:"start" calls the same code path as a real OSC 133 A mark, action:"end" the same as a real D mark. Both land in the identical CommandBlock record shape in terminals.ts (promptLine/commandLine/executionLine/endLine/ exitCode/promptText) — promptText is the one field that distinguishes an agent-turn block (populated) from a real shell command or a scrape-fallback block (always null). One record shape, one renderer, three possible producers.

Correction for anyone assuming "green tick = success": block ticks are actually blue (translucent, exit 0 or unknown) or red (non-zero exit) — canvasTerminalMarks.ts. Green is a completely separate, independent tick marking the line where the user submitted a prompt (driven by ParsedEvent::UserInput), drawn on top of the block ticks so it's never hidden. Two tick systems on one scrollbar, not one. CommandOverview.tsx is the panel that lists blocks with duration and command text, preferring promptText and falling back to slicing the grid between commandLine/executionLine when it's null.

Why It's Shaped This Way

4 things that look like bugs and aren't (quite)

A confident hook signal can still be a false alarm

Covered in full in OSC 777 vs 7770 — Notification's hook-driven state=awaiting couldn't distinguish a genuine block from Claude's own idle heartbeat, and unlike the OSC 777 path it mirrors, had no low-confidence escape hatch. Fixed 2026-09-02 — see the matching Incident Log entry for the mechanism; kept here so the next person can see why the hook path used to need one.

Block-source switching is one-way and permanent

Once a session has emitted a single OSC 7770 state= event, the screen-scrape block detector never runs again for that session's life — even if the hook later goes quiet (a crashed hook binary, a settings rollback mid-session). The alternative — falling back to scraping whenever the hook stream looks stale — would mean two block granularities (per-turn vs per-tool-call) interleaving unpredictably in the same scrollbar. A permanent switch, flipped once real hook evidence exists, keeps one session's ticks internally consistent even at the cost of never recovering if the hook stream dies mid-session.

OSC 133 zones and AgentBlock stay separate systems despite converging on screen

They could have been unified in the backend too. They aren't, because they answer different questions at different layers: OSC 133 answers "what did the shell run and what did it print," queried on demand from live cell tags; AgentBlock answers "when did the agent's turn start and end," pushed as a discrete lifecycle event. Merging them would mean deciding what a "prompt" means for an agent turn that has no real shell prompt line at all — the frontend convergence (one CommandBlock shape, reused handler) gets the visual benefit without forcing that decision on the backend.

Amp/Cursor/Droid's stuck-busy behavior is a tracked gap, not a design choice

These three (and Goose, for busy/idle specifically) have no screen classifier at all — a long-lived foreground command leaves them BUSY for the rest of the process. This was a deliberate deferral, not a decision that they don't need one: none of the four binaries was installed on the auditing machine to capture real screens against, and a classifier written against guessed screen shapes is worse than no classifier (it can confidently assert the wrong thing). Tracked in to-test.md; give each one an adapter only after capturing its actual output.

Incident Log

real, live-reproduced cases

Each entry below is a real production report, not a hypothetical. Kept chronological and never deleted — a fixed root cause is marked fixed, not removed, because the symptom ("badge stuck on awaiting") has more than one independent cause and a future report matching the same symptom needs to see everything already ruled in or out.

2026-09-01 — two live sessions stuck "awaiting" through full task completionfixed

Reported: commerce-journal's publish tab and agent-tooling-analysis's tool-scan tab both read "awaiting" despite being genuinely idle — both had finished their entire task (one published 37 Teams cards and printed a recap, the other completed a background scan) with the badge never clearing.

Root cause: both sessions are hook-instrumented Claude, running unattended with auto-approve/bypass-permissions on (⏵⏵ auto mode on). A real AskUserQuestion tool call fired mid-turn — the ordinary case, shell already SHELL_BUSY before and after, since PreToolUse(AskUserQuestion)'s awaiting override never touches the shell busy/idle bit at all (no SHELL_AWAITING exists). Claude answered its own question (auto-mode, no human at the keyboard). claude_hook_map()'s PostToolUse(AskUserQuestion| ExitPlanMode) busy re-affirmation — kept specifically to clear the badge afterward — fired into tuic_state_awaiting_event, but busy_transitioned was false (no real shell edge, already busy), so the clear it exists to provide was silently dropped. Nothing else is allowed to touch a confident question besides real user input, which never arrived. Silent because tuic_state_awaiting_event's old signature had no log on the dropped path — "the hook fired but got swallowed" and "the hook never fired" were indistinguishable from the logs alone; diagnosing this needed reconstructing the timeline from [Notify]/ [ChoicePrompt] frontend log lines and reading the source, not a log line pointing straight at it.

Separately found in the same investigation: the numbered-dialog ChoicePrompt screen-scrape detector had no hook-instrumented suppression at all — suppress_heuristic_question only ever covered the generic Question type. Live logs showed a hook-instrumented session logging both [ChoicePrompt] ... title="Do you want to proceed?" (screen-scrape) AND a hook-driven confident question — awaitingInput transition for the exact same dialog, seconds apart — a confusing duplicate signal, not two real events. (This one turned out not to be load-bearing for the stuck badge itself — the choice_prompt field it sets gets cleared by the same user-input event arm that the busy-clear fix above now correctly fires — but it was real noise worth removing on its own, and is the same "screen-scrape not suppressed under hooks" shape as Grok's OSC-0 heuristic below.)

Fix (this branch): tuic_state_awaiting_event gained a currently_awaiting parameter — the busy clear now fires on busy_transitioned || currently_awaiting, so a session that IS awaiting always gets its clear on the next busy re-affirmation, edge or no edge. ChoicePrompt detection is now skipped outright when the session is hook-instrumented. Both covered by regression tests replaying the real failure shape through the production process_chunk hot path (claude_askuserquestion_midturn_busy_reaffirmation_clears_stuck_awaiting, test_chunk_processor_choice_prompt_suppressed_when_hook_instrumented in pty.rs), each independently confirmed to fail against the pre-fix code.

Debug logging added throughout the state-transition path specifically so the NEXT report in this class doesn't need this same archaeology — see Investigation Playbook below for what to check and how to read it.

2026-08-29 — Notification hook's blanket confident latchfixed

Reported (2026-09-02): a live session (dbsql-test-review, databricks-sql-cli) finished its task, printed its recap, then ~44s later flipped to "awaiting" with an empty question text — the tab badge read "waiting for input" even though nothing was actually pending. Reconstructed from debug action=logs: a [Notify] … completion line, then 44s of silence, then a fresh question — awaitingInput transition with confident: true, question_text: "". That shape — confident, empty text, tens of seconds after a real completion — is exactly this card's mechanism, not the 2026-09-01 one below (no AskUserQuestion ever fired here).

See OSC 777 vs 7770's "confidence gap" reason card for the full root cause. Short version: Notification's hook-driven state=awaiting used to be always confident: true, with no way to distinguish a genuine block from Claude's own ~60s idle-timer heartbeat firing the same hook with the same ambiguous wording. This is a DIFFERENT mechanism from the 2026-09-01 incident above — that one is a real, correctly-confident AskUserQuestion block whose CLEAR got dropped; this one was a signal that was never entitled to be confident in the first place. Both produce the identical externally-visible symptom ("stuck on awaiting, agent genuinely idle"), so ruling one out is not evidence against the other — check both.

First pass: tuic_state_awaiting_event (pty.rs) classified the notify= verb's scraped message text exactly like parse_osc777_notifies already does for its own wording — "needs your permission" / "approval required" → confident, everything else → confident: false.

Refined the same day once Claude Code's actual, documented notification_type enum was in hand — far more reliable than sniffing free-text wording. Real production evidence for the exact root cause: the temporary hook-debug log (Investigation Playbook step 4) for this very session shows Stop at 20:42:39Z, then Notification{message: "Claude is waiting for your input", notification_type: "idle_prompt"} at 20:43:39Z — exactly 60s later, nothing fired in between. tuic-hook now also scrapes notification_type as a new notifytype verb (paired with notify, both immediately before state=awaiting, same write_all). pty.rs's notification_awaiting_outcome classifies deterministically off the 12 documented values: permission_prompt/elicitation_dialog/ elicitation_url_dialog/agent_needs_input/ quota_auto_resume_stale stay confident; auth_success/ elicitation_complete/elicitation_response/agent_completed/ quota_auto_resume_fired/quota_auto_resume_disabled are pure lifecycle noise and never badge awaiting at all; idle_prompt gets the sharpest fix — dropped outright (not merely non-confident) whenever the shell is already idle, since that means a real Stop already ended the turn and any future need for input arrives through its own signal the next time the user acts, exactly as suggested when this incident was reported. The same idle_prompt firing mid-turn (shell still busy, no Stop yet — the one gap this signal covers, an un-hooked plan/skill picker) still surfaces non-confidently. A notification_type this binary predates, or its total absence (an older Claude Code build), falls back to the original wording classifier — never a fixed guess, since guessing either direction risks silently swallowing a real future block or reproducing this exact incident under a new type name. No preceding notify=/notifytype= at all (the PreToolUse(AskUserQuestion|ExitPlanMode) and Elicitation case — neither ever scrapes either field) stays unconditionally confident, unchanged from before. Covered by pure-function unit tests per outcome (blocking/informational/idle-prompt-suppressed/ idle-prompt-mid-turn/unrecognized-type-fallback/no-type-fallback) and wire-level tests driving the real three-sequence notify→notifytype→state=awaiting bytes through the production process_chunk hot path (notification_hook_idle_prompt_after_stop_is_suppressed_through_process_chunk and siblings).

Grok's OSC-0 "Action Required" heuristic — unsuppressed under hook instrumentationopen

Noted in the Per-Agent Matrix: Grok's hook map has no narrow awaiting override at all (bare PreToolUse → busy only), so awaiting comes exclusively from the OSC-0 title heuristic — and unlike Claude's ChoicePrompt case above, this one hasn't been checked against suppress_heuristic_question or fixed. Flagging here so it isn't independently "discovered" a third time; same shape, different agent.

Gemini's Notification → awaiting is still unconditionally confidentopen

The exact same idle-timer-latch class of bug the 2026-09-02 Claude fix above closes — unfixed for Gemini. Noted in the Per-Agent Matrix: Gemini's hook map never goes through tuic-hook's stdin-JSON derivation at all (it passes a bare --state awaiting flag for its own Notification event), so there is no message/notification_type to scrape or classify even in principle. Fixing this needs Gemini's own hook confirmed to send `hook_event_name`-shaped stdin first — a real verification gap noted in `agent_hook.rs`'s own module doc comment, predating this session — not just reusing `notification_awaiting_outcome`. Flagging here so it isn't mistaken for already covered by today's fix, and isn't independently "discovered" again later.

Investigation Playbook

for the next "stuck/wrong state" report

Written for an agent picking up a fresh report with no other context — Boss will launch a new session, point it at this doc and at the specific TUIC session/tab that needs research. Read Three Origins and OSC 777 vs 7770 first if you haven't; this is the "what to actually go do" checklist.

1. Get the facts before theorizing

Use the tuicommander MCP tools against the live TUICommander instance (never guess from memory): session action=list to find the stuck session, session action=output to read its actual on-screen transcript (is a dialog really still there, or is the terminal idle and the badge just wrong?), debug action=logs (no level filter — default is info) to pull the frontend's [Notify]/[ChoicePrompt] lines and build a timeline of when awaitingInput actually flipped, and how long ago.

2. Check whether hook instrumentation is actually installed and live

Hooks install into the AGENT's OWN global settings file (~/.claude/settings.json for Claude — NOT anywhere per-repo), tagged # tuic-managed-hook. Grep that file for the sentinel to confirm hooks are installed at all before assuming a hook-driven signal is in play — a repo with no hooks installed can only be getting awaiting from screen-scrape or (for Claude) a native OSC 777 notify, if that ever actually fires (see below).

3. Read the new debug logs (2026-09-01) — but you need RUST_LOG=debug

The app's default tracing level is info (app_logger.rs) — tracing::debug! calls are silently dropped unless the process was launched with an elevated filter. To see them for a research window, launch TUICommander (or make dev) with, e.g.:

RUST_LOG=info,tuicommander_lib::pty=debug,tuicommander_lib::state=debug

What's logged, all at debug, all searchable via GET /logs once elevated:

  • state.rs's AppEvent::PtyParsed reducer — ONE generic log line whenever awaiting_input/question_confident/choice_prompt/ question_text actually changes, with before/after values and the triggering event_type. Covers every arm (question, question-cleared, user-input, choice-prompt, choice-cleared, status-line) — a new arm added later inherits this for free.
  • state.rs's PtyExit handler — logs specifically when a session exits while STILL awaiting_input (a strong signal something upstream never cleared it).
  • pty.rs's transition_explicit_shell_state_with_hook — every real shell busy/idle edge attempt and result (prev/target/ transitioned), regardless of trigger (OSC 7770 state= or OSC 133 shell integration).
  • pty.rs's tuic_state_awaiting_event — logs specifically when the 2026-09-01 fix's edge-repair path fires (a busy re-affirmation with no real edge, kept alive only because the session was already awaiting).
  • pty.rs's emit_question_cleared_if_stale — logs when the silence-timer backstop is BLOCKED from clearing (session is stale-eligible but confident or choice-prompt-owned). If a stuck session never logs this line, the backstop was never going to be the fix — look at the busy-reaffirmation path or choice-cleared instead.
  • pty.rs's ChoicePrompt detection — logs every fresh (non-dedup) detection, only for non-hook-instrumented sessions post-fix.

4. Read the raw hook payloads, temporarily, if the above isn't enough

A temporary debug hook is installed globally (2026-09-01, tagged # tuic-debug-hook-2026-09-01 (temporary, research) in ~/.claude/settings.json) on every Claude Code hook event TUIC cares about (SessionStart, UserPromptSubmit, PreToolUse (both the broad and AskUserQuestion|ExitPlanMode matchers), PostToolUse (same two), PostToolUseFailure, Notification, PermissionRequest, Elicitation, ElicitationResult, Stop, StopFailure, SessionEnd, SubagentStop). It appends one line per hook fire — UTC timestamp + the full stdin JSON (capped at 20KB, newlines squashed) — to .claude/hook-debug.log relative to whatever repo the session is running in (only when TUIC_SESSION is set, so it's silent outside TUIC). This is how the 2026-09-01 incident's root cause was originally traced for the WIP fixture that produced claude_double_askuserquestion_second_missed.tcap — reuse it rather than re-inventing it. Left in place intentionally, "for the time being" — remove it (grep the sentinel across all four hook-event blocks it touches) once this research window closes; it is NOT meant to ship in a release config.
