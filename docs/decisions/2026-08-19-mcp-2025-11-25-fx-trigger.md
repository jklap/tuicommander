# Advance the Legacy MCP Revision for fx Compatibility

## Status

Accepted on 2026-08-19 under the trigger Boss recorded in story `500-ab94`:
advance the legacy revision when a real client sends a 2026-07-28
`server/discover` request or per-request protocol metadata.

## Problem

The official fx 0.0.3 binary is that real client. It first sends
`server/discover` with protocol `2026-07-28`, receives TUICommander's deliberate
method-not-found response, and falls back to legacy initialization with
`2025-11-25`. Before this decision, TUICommander responded with `2025-03-26`
regardless of the offered legacy revision.

Native evidence shows fx repeats the negotiation three times, never sends
`tools/list`, and exposes no TUIC tools. The same bridge and socket return the
complete tool catalog to a direct legacy client, proving that configuration,
process launch, and the bridge transport work and that the revision mismatch is
the failing boundary.

## Decision

Implement only Phase B1 of the approved dual-era MCP plan.

- The legacy server initialize response advances to `2025-11-25`.
- TUICommander's HTTP and stdio upstream clients offer `2025-11-25`.
- `tuic-bridge` opens its internal session at `2025-11-25` and sends an
  `MCP-Protocol-Version` HTTP header derived from the proxied request, falling
  back to `2025-11-25` when a legacy request carries no per-request version.
- Requests without the version header remain accepted for older clients. No
  existing session, SSE, identity, tools/list, or tools/call semantics change.

This is a legacy compatibility step, not the modern-era migration. The server
continues returning method-not-found for `server/discover`; fx's specified
legacy fallback is the supported path.

## Existing Mechanisms and Reuse

The change reuses the existing `/mcp` initialize/session flow, bridge replay,
tool catalog, tool-call dispatcher, and upstream proxy clients. It does not add
a parallel fx adapter or a second MCP server. The authoritative implementation
plan remains `plans/mcp-2026-07-28-dual-era.md`, Phase B1.

## Alternatives Considered

1. Advertise fx MCP support while leaving installation non-functional. Rejected
   because the official client never receives a tool catalog.
2. Disable fx MCP auto-installation. Rejected because a real client has now met
   Boss's explicit upgrade trigger, and the bounded legacy phase is sufficient.
3. Rewrite responses inside `tuic-bridge` while the server remains pinned.
   Rejected because it would make the adapter claim protocol semantics the
   authority does not expose.
4. Implement modern `server/discover` and the entire dual-era transport now.
   Rejected because fx has a defined legacy fallback and Phases D–G change
   materially broader headers, identity, subscriptions, and task contracts.

## Trade-offs

Legacy clients will see a newer negotiated revision in the initialize result.
The actual TUIC tool and session surface remains unchanged, so compatibility
risk is limited to clients that incorrectly require the server to echo
`2025-03-26`. The existing transport suite and native Claude/Codex-era paths
must remain green before delivery.

Keeping `server/discover` unsupported means fx performs one failed probe before
using its legacy fallback. That bounded startup cost avoids
claiming modern semantics before their planned validation and security work is
implemented.

## Failure Semantics

An unsupported modern discovery request continues to return JSON-RPC `-32601`.
The bridge forwards the response unchanged. A subsequent legacy initialize is
accepted and returns `2025-11-25`; tool discovery then follows the existing
session-bound path. Missing protocol headers remain compatible with older
clients. Transport, authentication, or tool-list failures retain their current
typed errors and do not fall back to a fabricated catalog.

## Lifecycle and Ownership

TUICommander owns the negotiated legacy server revision and its upstream client
offers. fx owns the decision to probe modern discovery and fall back. The bridge
owns faithful stdio-to-HTTP transport and version-header projection, but never
invents server capabilities. The remaining modern-era phases stay tracked by
the approved plan and their existing stories.
