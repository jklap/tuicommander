# Workflow definitions

Workflow definitions are owned by a canonical project path and stored in `workflows.sqlite3` under the TUICommander configuration directory. A definition has a mutable draft revision and immutable published revisions. Editing a draft uses an expected revision; publishing validates the graph, resolves pinned story-template revisions, and inserts a new published row in one SQLite transaction. A run must pin a published revision; this definition layer does not execute nodes.

Each definition has a `closure` policy. Existing records migrate to `human`, and new drafts default to `human`; this legacy policy name means an explicit approval transition, which may be performed by any trusted caller. `update_closure` edits a draft with an expected revision. `automatic` can be saved as a draft but publishing it is refused until TUIC has an automatic evidence gate. Published revisions retain their pinned closure policy.

A definition also pins `requiredChecks`: up to 16 check commands, each with a stable ID, an `argv` array, and a timeout of 1–600 seconds. `update_checks` edits the draft with an expected revision; publication stores the exact set on that immutable revision. Commands invoke executables directly, without a shell. `execute_check` runs a pinned check in the assigned, clean story worktree and appends a durable `CheckRecorded` event with command, exit code, branch ref, commit/tree digest, and duration. A failed command also receives a receipt, but it cannot authorize integration. A changed worktree or ref makes the receipt stale.

The graph contains stable node IDs and directed edges. Node kinds are Start, Agent, Create Stories, Story Dispatch, Judge, Gate, Pause, Loop, Join, Notify, and End. An Agent carries a role, prompt template, and a bounded list of supported capabilities. Story Dispatch is a plan-only node that pins a published story definition ID and revision in the same project. Create Stories is plan-only. Join is story-only, with at least two incoming branches. A Loop is the only source of a back edge and requires `max_iterations` from 1 through 100 plus `repeat` and `exhausted` edges. Judge requires `yes`, `no`, and `uncertain`; Gate requires `pass` and `fail`; Story Dispatch requires `completed` and `blocked`. Invalid references, duplicate or unreachable nodes, missing outcomes, and other cycles are rejected on publish.

The first list or explicit seed action inserts `Story delivery` and `Resolve plan` once per project. The latter pins revision 1 of the former. Both remain editable as drafts; a new published revision does not rewrite an older one.

Desktop IPC command `workflow_definition_action` and HTTP `POST /workflows/definition/action?path=<project>` call the same Rust service. Actions: `seed_templates`, `create_draft`, `list_drafts`, `get_draft`, `update_draft`, `publish`, `get_published`. The action is a JSON object tagged by `action`; replies are tagged `{ type, value }`. The Plans and Stories dialog has a Designer tab for draft selection, drag/drop or button-based node addition, edge connection, node inspection, saving and publishing. The backend remains the authority for graph validation at publication.

## Durable runs

`run/` stores plan runs in `<config dir>/workflow_runs.sqlite3`. A run pins a published plan revision, the Story Dispatch node's published story revision, and the canonical checkout's branch ref when Git exposes one. An immediate SQLite transaction appends each sequenced event and replaces its run, story-execution, node-attempt, and effect-intent projections. `replay` folds the event stream through a pure reducer; `events_after` pages at most 500 events from a sequence cursor. Clients should re-read by cursor after reconnecting.

Commands have caller-supplied IDs bound to their payload hashes and an expected run sequence. A retry returns the original receipt; a reused ID with a different payload fails, as does a stale expected sequence. Runs enforce one active instance per plan, loop/story-creation/spawn/duration budgets, a maximum of two concurrent story attempts by default (configurable from one to eight), and generation-fenced attempt reports. Running story attempts with unknown, globbed, or overlapping file scopes are serialized. For a plan with a workflow run, a prerequisite counts for dependent release only when it has a `StoryIntegrated` receipt at its accepted revision; the same predicate gates manual start, managed claim, workflow dispatch, and final run verification. A plan with no workflow run instead releases dependents as soon as every prerequisite is Done. A report for an old generation remains an audit event without advancing the attempt. Agent attempts start only on Agent nodes in the pinned story graph.

Before spawning an agent or creating a story, the runtime reserves a stable effect key. The first workflow use after desktop or headless startup opens the run database and reconciles active runs before accepting new work, so startup does not scan runs and new work cannot race recovery: unfinished attempts become interrupted, intended external effects become uncertain, and every active run pauses for an explicit resume decision. Restart recovery runs once per database path in each process. A failed run is logged and skipped so recovery continues for other runs; later opens do not retry it. The database-path mutex is released before recovery and dependency checks. Normal runtime reconciliation refreshes dependencies without interrupting live attempts or changing intended effects. Effects are never repeated automatically. An operator must resolve each uncertain effect before resuming. Reconciliation also repairs dependent readiness from committed integration events after a crash. Planning closure stores a fingerprint of the current story set and requirements. The next command reopens planning if that set changes. Completion also requires every story to be Done, accepted, and integrated at its current revision, no active attempts or uncertain effects, and a current final-verification fingerprint. The runtime currently records the final-verification decision supplied by the caller; the policy and evidence gate are part of the later evaluation slice.

`workflow_run_action` and `POST /workflows/run/action?path=<project>` expose `start_plan`, `get`, `list_plan_runs`, `events`, `command`, `execute_check`, `record_integration`, and `recertify_canonical` using the same Rust service and canonical project checks. `list_plan_runs` returns the newest run snapshots for a plan with a limit of 1–100, so a timeline can discover its durable run ID. `record_integration` records an already completed, non-fast-forward merge: TUIC verifies that the checked source commit is the merge's second parent, the canonical checkout is clean, and all pinned checks pass again on the merge result. The receipt records canonical ref, base/source/result commits and trees, accepted story revision, and post-integration check receipts. The merge itself remains an explicit operator action in this slice. An out-of-band ref or tree change invalidates the prior tip's evidence. `recertify_canonical` runs the pinned checks on the clean new tip, verifies every integrated source commit is still an ancestor, and appends a durable `CanonicalRecertified` event. This receipt-only action remains available after a run completes or cancels, because other plans can depend on its integrated stories. A later ref, commit, or tree change invalidates that event too. This is an operator API. Agent binding and typed reports are refused on this API; they require the managed MCP session.

## Managed agent attempts

The `workflow_launch` MCP tool accepts a run attempt and a Git worktree path already registered under the project. A plan attempt stays in the caller's isolated worktree. A story attempt may use another registered isolated worktree: the active coordinator assigns it in a durable event before worker spawn, and another story in the run cannot use that worktree. Later attempts for that story reuse the assignment. The service does not create, integrate, or remove those worktrees yet. For a plan attempt, it renders the pinned coordinator or planner prompt with plan source, current stories, revision and sequence cursor. For a story attempt, it renders the pinned role prompt with criteria, file scope, feedback, skill references and stable IDs. It redacts the delivered prompt, bounds it to 32 KB, and stores its contract version, SHA-256 hash and redacted preview. A story worker launch requires the calling PTY to own a running coordinator attempt in that run.

The engine reserves a spawn effect before calling the managed `agent spawn` path. The resulting PTY session and task handle are bound to the attempt in a durable event that also completes the effect. An already reserved spawn is never retried automatically; reconciliation pauses an uncertain run. Cancellation marks unfinished attempts interrupted and intended effects uncertain; a child that starts before the failed binding is killed. The `workflow_report` MCP tool resolves the calling live PTY itself and accepts a typed report only for its bound attempt and current story revision. The report and criterion evidence are durable events. A pause prevents new work but preserves current-generation reports from already running parallel attempts. Duplicate identical reports return the original receipt; a different payload for the same attempt is rejected. PTY exit interrupts an unresolved attempt and pauses the run, regardless of exit code. The operator and browser clients receive the same `workflow-run-changed` cursor hint and replay events from storage.

A `needs_input` report includes `inputRequest {question,options}` and pauses the run. The operator command `answer_input {attempt_id,answer}` appends an answer event; the run remains paused until an explicit `resume`. An unanswered request blocks resume and final verification. A completed reviewer report includes `review {decision,artifactDigest,findings}`; each finding names a criterion index, severity, summary, and evidence. This is advisory evidence tied to the reported story revision, and does not change story status. After a committed story-worker report, the active coordinator gets inbox mail containing only the run ID, story ID and durable sequence cursor; it must read the event log for the actual result. Late or duplicate reports do not send a fresh wake. The review policy and artifact verification are separate work.

Launching attempts is explicit in this slice. Automatic graph scheduling, evaluation and review policy are subsequent slices.

The active plan coordinator can call `workflow_story_create` with a stable proposal key. The story store commits the key and story in one transaction, so a lost MCP response and retry cannot create duplicates. The run separately reserves a bounded CreateStory effect and records its outcome; a crash between the two databases leaves an uncertain effect for operator reconciliation. A read-only proposal lookup can establish whether the story was committed, but the creation tool refuses uncertain effects and never replays them. A reused key with different content is rejected.

Published checks own their process trees (Unix process groups; Windows suspended
job assignment with kill-on-close). Cancelling a run synchronously stops its
active checks and fences late starts. Host shutdown tears down every active check
before exit; cancellation yields no successful receipt.

Workflow actors are tracking metadata, not action permissions. Desktop IPC and credential-authenticated HTTP imply Human; sessionless local HTTP (including missing caller-address metadata on Unix sockets) implies LocalApi. Managed story calls record their session identity. Local token exchange is accepted. Actor identity never refuses story or workflow actions; state, revision, project and integration checks still apply. The actor is host-selected; request JSON cannot choose it.

Plan aggregation uses the same receipt freshness authority as dependency release and final verification. Workflow-owned plans are Done only while every approved story has current integration evidence at its accepted revision; ref movement returns Active until recertification. Manual plans keep Done/WontFix aggregation. Explicit recertification remains available after cancellation to renew already integrated evidence.

Git receipt and dependency probes run before SQLite write transactions and before the story-store mutex is acquired. The short commit transaction revalidates the persisted run sequence and relevant story revisions; a concurrent change fails with a retry error. No filesystem fingerprint is persisted: ref movement after a probe invalidates receipt freshness on the next read.
