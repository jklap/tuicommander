# Workflow definitions

Workflow definitions are owned by a canonical project path and stored in `workflows.sqlite3` under the TUICommander configuration directory. A definition has a mutable draft revision and immutable published revisions. Editing a draft uses an expected revision; publishing validates the graph, resolves pinned story-template revisions, and inserts a new published row in one SQLite transaction. A run must pin a published revision; this definition layer does not execute nodes.

The graph contains stable node IDs and directed edges. Node kinds are Start, Agent, Create Stories, Story Dispatch, Judge, Gate, Pause, Loop, Join, Notify, and End. An Agent carries a role, prompt template, and a bounded list of supported capabilities. Story Dispatch is a plan-only node that pins a published story definition ID and revision in the same project. Create Stories is plan-only. Join is story-only, with at least two incoming branches. A Loop is the only source of a back edge and requires `max_iterations` from 1 through 100 plus `repeat` and `exhausted` edges. Judge requires `yes`, `no`, and `uncertain`; Gate requires `pass` and `fail`; Story Dispatch requires `completed` and `blocked`. Invalid references, duplicate or unreachable nodes, missing outcomes, and other cycles are rejected on publish.

The first list or explicit seed action inserts `Story delivery` and `Resolve plan` once per project. The latter pins revision 1 of the former. Both remain editable as drafts; a new published revision does not rewrite an older one.

Desktop IPC command `workflow_definition_action` and HTTP `POST /workflows/definition/action?path=<project>` call the same Rust service. Actions: `seed_templates`, `create_draft`, `list_drafts`, `get_draft`, `update_draft`, `publish`, `get_published`. The action is a JSON object tagged by `action`; replies are tagged `{ type, value }`. Graph editing, scheduler, coordinator, and execution APIs are separate later slices.

## Durable runs

`run/` stores plan runs in `<config dir>/workflow_runs.sqlite3`. A run pins a published plan revision and the Story Dispatch node's published story revision. An immediate SQLite transaction appends each sequenced event and replaces its run, story-execution, node-attempt, and effect-intent projections. `replay` folds the event stream through a pure reducer; `events_after` pages at most 500 events from a sequence cursor. Clients should re-read by cursor after reconnecting.

Commands have caller-supplied IDs bound to their payload hashes and an expected run sequence. A retry returns the original receipt; a reused ID with a different payload fails, as does a stale expected sequence. Runs enforce one active instance per plan, loop/story-creation/spawn/duration budgets, and generation-fenced attempt reports. A report for an old generation remains an audit event without advancing the attempt. Agent attempts start only on Agent nodes in the pinned story graph.

Before executing an external action, the runtime reserves a stable effect key. Desktop and headless startup reconcile active runs: unfinished attempts become interrupted, intended external effects become uncertain, and every active run pauses for an explicit resume decision. Effects are never repeated automatically. An operator must resolve each uncertain effect before resuming. Planning closure stores a fingerprint of the current story set and requirements. The next command reopens planning if that set changes. Completion also requires every story to be Done and accepted at its current revision, no active attempts or uncertain effects, and a current final-verification fingerprint. The runtime currently records the final-verification decision supplied by the caller; the policy and evidence gate are part of the later evaluation slice.

`workflow_run_action` and `POST /workflows/run/action?path=<project>` expose `start_plan`, `get`, `list_plan_runs`, `events`, and `command` using the same Rust service and canonical project checks. `list_plan_runs` returns the newest run snapshots for a plan with a limit of 1–100, so a timeline can discover its durable run ID. This is an operator API. Agent binding and typed reports are refused on this API; they require the managed MCP session.

## Managed agent attempts

The `workflow_launch` MCP tool accepts a run attempt and a Git worktree path already registered under the project. In this slice the worktree must equal the caller's isolated worktree; run-owned per-story worktrees come with the scheduler. For a plan attempt, it renders the pinned coordinator or planner prompt with plan source, current stories, revision and sequence cursor. For a story attempt, it renders the pinned role prompt with criteria, file scope, feedback, skill references and stable IDs. It redacts the delivered prompt, bounds it to 32 KB, and stores its contract version, SHA-256 hash and redacted preview. A story worker launch requires the calling PTY to own a running coordinator attempt in that run.

The engine reserves a spawn effect before calling the managed `agent spawn` path. The resulting PTY session and task handle are bound to the attempt in a durable event that also completes the effect. An already reserved spawn is never retried automatically; reconciliation pauses an uncertain run. Cancellation marks unfinished attempts interrupted and intended effects uncertain; a child that starts before the failed binding is killed. The `workflow_report` MCP tool resolves the calling live PTY itself and accepts a typed report only for its bound attempt and current story revision. The report and criterion evidence are durable events. Duplicate identical reports return the original receipt; a different payload for the same attempt is rejected. PTY exit interrupts an unresolved attempt and pauses the run, regardless of exit code. The operator and browser clients receive the same `workflow-run-changed` cursor hint and replay events from storage.

Launching attempts is explicit in this slice. Automatic graph scheduling, evaluation and review policy are subsequent slices.

The active plan coordinator can call `workflow_story_create` with a stable proposal key. The story store commits the key and story in one transaction, so a lost MCP response and retry cannot create duplicates. The run separately reserves a bounded CreateStory effect and records its outcome; a crash between the two databases leaves an uncertain effect for operator reconciliation. A read-only proposal lookup can establish whether the story was committed, but the creation tool refuses uncertain effects and never replays them. A reused key with different content is rejected.
